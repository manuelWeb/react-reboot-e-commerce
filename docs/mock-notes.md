# Mock API notes

## Purpose

The application uses Mock Service Worker (MSW) to simulate the catalogue API
without introducing a backend. Application code still performs standard HTTP
requests and does not depend on MSW directly.

```text
Application → fetch('/api/products') → MSW → mocked HTTP response
```

The product fixture is stored locally so development and tests remain
deterministic and can run without access to an external product service.

## Refreshing the product fixture

The sample product content is adapted from
[DummyJSON Products](https://dummyjson.com/products).

To generate a new sample, change the `limit` query parameter and run the
following snippet in a browser console:

```js
fetch(
  'https://dummyjson.com/products?limit=6&select=id,title,price,category,thumbnail,stock',
)
  .then((response) => {
    if (!response.ok) {
      throw new Error(`Request failed with status ${response.status}`)
    }

    return response.json()
  })
  .then(({ products }) =>
    products.map(({ id, title, price, category, thumbnail, stock }) => ({
      id: String(id),
      name: title,
      category,
      imageUrl: thumbnail,
      priceInCents: Math.round(price * 100),
      availability: stock > 0 ? 'available' : 'unavailable',
    })),
  )
  .then((products) => {
    console.log(JSON.stringify(products, null, 2))
  })
  .catch(console.error)
```

Copy the generated JSON into:

```text
src/mocks/data/products.ts
```

Keep the compile-time contract check:

```ts
import type { Product } from '@/features/products/product'

export const products = [
  // Generated and reviewed products.
] satisfies Product[]
```

Review generated data before committing it:

- retain products from several retail categories;
- include at least one unavailable product for UI and test scenarios;
- confirm that image URLs use HTTPS;
- keep prices expressed as integer cents;
- avoid importing the complete external response schema.

DummyJSON is only a source for fixture content. The application must not call it
at runtime.

## Service Worker in the browser

A Service Worker is a browser-managed, event-driven script that can intercept
network requests made by pages within its scope. It runs separately from the
page, has no direct access to the DOM, and can be stopped and restarted by the
browser.

MSW uses this mechanism to intercept requests at the network boundary:

```text
React application
    ↓ fetch('/api/products')
Browser
    ↓ fetch event
public/mockServiceWorker.js
    ↓ matches the request against the application handlers
src/mocks/handlers.ts
    ↓
HttpResponse.json(products)
    ↓
React receives a normal Fetch API Response
```

`public/mockServiceWorker.js` is generated by MSW and must not be edited
manually. Regenerate it after relevant MSW upgrades with:

```bash
npx msw init public --save
```

The generated worker is generic. Business-specific routes and response data
remain in `src/mocks/handlers.ts` and `src/mocks/data/`.

The browser integration uses `setupWorker(...handlers)`. MSW should start before
React renders so the first application request cannot escape interception.
Enable the worker in development only; a production application should call the
real API.

Service Workers require a secure context (HTTPS), with `localhost` supported as
a development exception. A worker only controls pages within its registered
scope. Serving `mockServiceWorker.js` from the application root gives it access
to the whole application.

MSW does not automatically cache responses or make the application a
Progressive Web App. It uses the Service Worker request-interception capability
to return controlled HTTP responses.

## Request handlers

Handlers describe the simulated network:

```ts
import { http, HttpResponse } from 'msw'

import { products } from './data/products'

export const handlers = [
  http.get('/api/products', () => {
    return HttpResponse.json(products)
  }),
]
```

Handlers are stored in an array because MSW accepts multiple endpoint
definitions and reuses the same collection in different environments:

```ts
setupWorker(...handlers) // Browser development
setupServer(...handlers) // Vitest/Node
```

Unhandled requests may be configured differently:

- development can bypass requests that belong to real external services;
- tests should treat unexpected requests as errors.

## MSW in tests

Node.js does not run browser Service Workers. MSW therefore provides
`setupServer()` from `msw/node`. Despite its name, it does not open a TCP port;
it intercepts requests within the test process.

The test lifecycle is configured centrally:

```ts
beforeAll(() => {
  server.listen({ onUnhandledRequest: 'error' })
})

afterEach(() => {
  server.resetHandlers()
})

afterAll(() => {
  server.close()
})
```

`resetHandlers()` is important because individual tests can override the default
response to exercise empty catalogues, server failures, latency, and recovery.
Resetting after every test prevents one scenario from leaking into another.

Tests should assert observable HTTP or user behaviour instead of MSW
implementation details.
